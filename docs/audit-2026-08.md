## 1 · S1 — Search and Notifications authorize on org membership, not project permission

**Files:** `Modules/Search/Repositories/SearchRepository.cs:88-113`,
`Modules/Notifications/Repositories/Implementations/NotificationRepository.cs:18-58`

Both modules resolve the caller's access with the same query:

```csharp
await _context.OrganizationMemberships
    .Where(m => m.UserId == userId)
    .Select(m => m.OrganizationId)
    .ToListAsync(ct);
```

and then read **every active project in those organizations**.

This directly contradicts the permission model. `RolePermissions.AtOrganization` grants
`RoleType.Member` exactly one permission — `org:read` — and the model states plainly that
organization membership "grants nothing inside the organization." `docs/permissions-frontend.md` §9
repeats it: *"An org member on no team holding no project role still sees no projects."*

They see them here. An organization `Member` on no team, holding no project role:

- `GET /api/search?q=payment` returns work item **titles** from every project in the org.
- `GET /api/notifications` returns work item titles, changed field names, and new values from every
  project in the org.

`GET /api/projects/{id}` correctly returns 404 for the same user and the same project. Two endpoints
disagree about who may see a project's contents, and the permissive pair are the ones with no
`[RequirePermission]` attribute on them.

**Why the coverage test did not catch it.** `EndpointAuthorizationCoverageTests` asserts every action
carries either `[RequirePermission]` or `[NoPermissionRequired]`. Both of these carry the latter, with
a justification that is true as written and insufficient as a rule — "scoped to the organizations the
caller belongs to" is the bug, stated as the defence.

**Fix.** Resolve the readable project set from the access snapshot, not from membership. The snapshot
already holds direct project grants and team grants; the missing piece is expanding those into
project ids, which `AccessResolver` can do in one query. Give the RBAC module an
`IAccessResolver.GetReadableProjectIdsAsync(userId)` and route both modules through it. Then tighten
`[NoPermissionRequired]` so its justification string must name the resolver it delegates to —
"scoped to the caller" is not a justification, it is a description of every endpoint.

**Also review:** `WorkspaceController.GetSummary` and `.GetActivity` use the identical pattern.
`GetActivity` is the less severe case — activity rows are already filtered by the Activity module —
but `GetSummary`'s work item counts span projects the caller cannot open.

## 2 · S1 — Optimistic concurrency is plumbed through the whole stack and never applied

**Files:** `Modules/WorkItems/Models/WorkItem.cs:61`,
`Modules/WorkItems/Services/WorkItemService.cs:143-224`,
`Modules/WorkItems/Repository/WorkItemRepository.cs:196`

Every piece of the lost-update defence exists:

- `WorkItem.Version` maps to Postgres `xmin`, with a careful comment explaining that the real race is
  "A reads, B saves, A saves" and that closing it needs the client to send back the version it read.
- `UpdateWorkItemRequest.ExpectedVersion` and `UpdateWorkItemStateRequest.ExpectedVersion` exist.
- `WorkItemsController:112` passes `request.ExpectedVersion` into the service.
- `IWorkItemService.UpdateAsync` / `UpdateStateAsync` accept `long? expectedVersion`.
- `IWorkItemRepository.SetOriginalVersion(item, version)` exists and does exactly the right thing:
  `_context.Entry(item).Property(w => w.Version).OriginalValue = version`.

`SetOriginalVersion` is **never called from anywhere.** `UpdateStateAsync` accepts `expectedVersion`
and its body never reads the parameter. `UpdateAsync` does not accept it at all — the value sits
unread on the request object.

The client sends a version, the server takes it, ignores it, and last-write-wins silently. The
`WorkItem.Version` XML comment describes a guarantee the code does not make, which is worse than
having neither: it will be believed.

**Fix.** In both methods, after loading the entity and before `SaveChangesAsync`, call
`SetOriginalVersion` when `expectedVersion` is supplied, and translate
`DbUpdateConcurrencyException` into a 409 carrying the current version so the client can rebase.
Decide explicitly whether a missing `expectedVersion` means "I accept last-write-wins" (current
behaviour) or is rejected — recommend accepting it for now, rejecting it once the frontend sends it,
and saying which in the response.

This becomes load-bearing the moment git sync ships: a webhook worker and a human will write the same
row concurrently as a matter of routine, not as a rare race.

## 3 · S1 — The state machine lets work close without review

**File:** `Modules/WorkItems/Services/WorkItemService.cs:439-452`

```csharp
WorkItemState.New      => [Active],
WorkItemState.Active   => [Resolved, Closed],   // ← Active → Closed
WorkItemState.Resolved => [Closed, Active],
WorkItemState.Closed   => [Active],
```

`Active → Closed` lets the assignee mark their own work done without it ever being resolved, reviewed,
or tested. Every transition is gated on the same permission — `workitem:write` — which every
Contributor and every team member holds. There is no separate authority for *certifying* work,
so today the person who writes the code is the person who declares it finished.

That is incompatible with the QA gate the product requires. The replacement state machine and the
`workitem:verify` permission are specified in [`../build_context.md` §4](../build_context.md#4-the-qa-gate).

**Fix now, independent of the wider redesign:** drop `Closed` from the `Active` transition set. It
costs one line and closes the hole while the rest is designed.

## 4 · S2 — Every internal constant is hardcoded on the frontend because there is no endpoint for it

This is the issue flagged as causing frontend pain, and it is broader than roles and priority.

Enums serialize as **strings** on the wire (`Program.cs` registers a global
`JsonStringEnumConverter`), which is right — but it means the numeric values that carry meaning
server-side never reach the client. Every one of these is currently a hand-maintained clientside
copy:

| Constant | Defined in | What the client loses |
|---|---|---|
| `RoleType` (9 values, 3 scopes) | `Modules/Rbac/Models/Role.cs` | Which roles are valid at which scope; display labels; what each permits |
| `Permissions` (22 constants) | `Modules/Rbac/Models/Permissions.cs` | The entire vocabulary — the client cannot name a capability |
| `WorkItemPriority` | `Modules/WorkItems/Models/WorkItem.cs:32` | **Sort order.** `Critical=1 … Low=4` is meaningful; `"Critical"` on the wire is not |
| `WorkItemState` | same file, `:22` | Legal transitions, display order, which are "done" |
| `WorkItemType` | same file, `:9` | Legal parent→child pairs (`ValidateHierarchy` is server-only) |
| `SprintStatus` | `Modules/Sprints/Models/Sprint.cs:12` | Lifecycle order |
| `WorkItemLinkType` | `Modules/WorkItems/Models/WorkItemLink.cs` | Inverse-name pairing (`blocks` ↔ `blocked by`) |
| `TeamPositions.All` | `Modules/Rbac/Models/Role.cs` | Which team roles are singular appointments |

The priority case is the sharpest illustration. The server knows `Critical` sorts before `Low` because
the enum is numbered. The client receives four unordered strings and has no choice but to hardcode
`['Critical','High','Medium','Low']` — and that array is now a second source of truth that no test
covers and no migration updates.

`RolePermissions` already has the right instinct: `AssignableAt(scope)` exists precisely because "two
copies of which roles belong at project scope is one copy too many," and its remarks record that the
hand-maintained third copy is the one that silently fell behind. The frontend is currently that third
copy for eight different vocabularies.

**Fix.** A metadata endpoint that projects these from their definitions, with `value`, `label`,
`order`, and the relationships (valid scopes, legal transitions, allowed children, inverse link
names). Full contract in [`../build_context.md` §5](../build_context.md#5-metadata-and-capability-endpoints).
Two things make it durable rather than a fourth copy: it is generated from the same declarations the
evaluator reads, and a test asserts every enum member appears in the document.

## 5 · S2 — Capability is still not queryable

`docs/permissions-frontend.md` §10 already records this: *"Capability is still not queryable. Keep
deriving it from the role and membership data you already fetch, and treat 403/404 as
authoritative."*

Deriving it clientside now requires reimplementing `AccessEvaluator` in TypeScript — three inheritance
routes, the team→project edge with its Scrum Master / Product Owner exception, and OrgAdmin's reach.
That reimplementation will drift, and it will drift silently toward being *more* permissive, because
a UI that shows a button that 403s is a bug someone reports, while a UI that hides a button someone
is entitled to is a bug nobody reports.

The 404-on-denial split makes it worse: the client cannot distinguish "gone" from "forbidden," so it
cannot even learn capability by probing.

**Fix.** `GET /api/me/capabilities?scope=project:{id}` plus a batch form. It is a thin wrapper over
`IAccessResolver` — the snapshot is already loaded and cached per request. Contract in
[`../build_context.md` §5](../build_context.md#5-metadata-and-capability-endpoints).

## 6 · S2 — The outbox `NOTIFY` path is decorative

**Files:** `Shared/Kernel/Events/OutboxDispatcher.cs:220-233`,
`Shared/Data/Migrations/20260813004106_Phase1_OutboxAndIdempotency.cs:79-90`

The migration installs an `AFTER INSERT` trigger that calls
`pg_notify('boardsync_outbox', '')`. The dispatcher opens a dedicated connection, issues
`LISTEN boardsync_outbox`, and waits. All of that works.

The handler is:

```csharp
connection.Notification += (_, _) => _logger.LogTrace("Outbox notification received.");
```

It writes a trace line. It does not signal the dispatch loop. Meanwhile the loop's wait is:

```csharp
/// Sleeps until the poll interval elapses or a NOTIFY arrives, whichever is first.
private async Task WaitForWorkAsync(CancellationToken ct)
{
    await Task.Delay(TimeSpan.FromSeconds(_settings.PollIntervalSeconds), ct);
}
```

An unconditional 5-second sleep. The comment describes behaviour the method does not have.

**Consequence.** Event delivery latency is uniform 0–5s, averaging 2.5s — not the "milliseconds"
claimed in the class remarks, `OutboxSettings`, and the README. Every downstream feature inherits it:
the activity feed, realtime board updates, and the notification bell all lag by up to a poll interval.
`README.md` §4a tells operators `PollIntervalSeconds` is "the safety net for a dropped listener." It
is the only path.

**Fix.** Replace the `Task.Delay` with a wait on a signal the notification handler sets:

```csharp
private readonly SemaphoreSlim _work = new(0, 1);

// handler
connection.Notification += (_, _) => { try { _work.Release(); } catch (SemaphoreFullException) { } };

// wait
private async Task WaitForWorkAsync(CancellationToken ct)
{
    try { await _work.WaitAsync(TimeSpan.FromSeconds(_settings.PollIntervalSeconds), ct); }
    catch (OperationCanceledException) { }
}
```

The bounded semaphore collapses a burst of notifications into one wake, which is what you want — the
loop drains until a batch comes back short anyway. Keep the timeout: it stays the safety net the
docs already describe, and it becomes true.

that cannot run is worse than an absent one, because it costs a new contributor an afternoon.

## 8 · S2 — Work item update is full-replace only

**File:** `Modules/WorkItems/Services/WorkItemService.cs:143-190`

`UpdateAsync` unconditionally assigns every field from the request:

```csharp
item.Title       = request.Title.Trim();
item.Description = request.Description?.Trim();
item.Priority    = request.Priority;
item.AssigneeId  = request.AssigneeId;
item.StoryPoints = request.StoryPoints;
item.TeamId      = request.TeamId;
```

There is no `PATCH`. A client wanting to change only the assignee must send the complete current
object back, and anything it omits or has stale is written as the new truth. Combined with finding 2
(no concurrency check), two people editing different fields of the same item silently overwrite each
other — the exact failure the fractional-rank design in `SprintWorkItem.Rank` was introduced to
eliminate for ordering, left standing for fields.

The state machine is already split out into its own endpoint (`PATCH .../state`), which shows the
right instinct; assignment and priority deserve the same treatment. Git sync will make this acute:
the webhook worker wants to change exactly one field and must not touch the other five.

**Fix.** Add `PATCH /api/workitems/{id}` taking a sparse body, with explicit-null semantics
(distinguish "field absent" from "field set to null" — `JsonElement`, `Optional<T>`, or JSON Merge
Patch). Keep `PUT` as-is for full replace. Emit one `WorkItemUpdated` per field actually changed, as
`TrackChange` already does.

## 9 · S3 — Search is a sequential scan with no ranking

**File:** `Modules/Search/Repositories/SearchRepository.cs`

Every predicate is `x.Field.ToLower().Contains(term)`, which Npgsql translates to
`lower(field) LIKE '%term%'`. Non-sargable — no index can serve it, so each of the four search
methods scans its table in full. `WorkItems` is the fastest-growing table in the system.

Ordering is `CreatedAt DESC` for work items and alphabetical elsewhere. There is no relevance
ranking, so an exact title match sorts below an unrelated newer item that happens to contain the term
as a substring. There is no pagination — a hard `take` and no cursor.

Not urgent at current volume, and it degrades on a curve rather than a cliff. Worth fixing before the
AI report layer starts querying it.

**Fix.** Postgres full-text search: a stored `tsvector` column on `WorkItems` (title weighted `A`,
description `B`) with a GIN index, queried by `websearch_to_tsquery` and ordered by `ts_rank_cd`.
Keep trigram (`pg_trgm` + GIN) for the member/org/project lookups where substring matching on short
names is genuinely what is wanted. No new infrastructure — this is why Postgres was the right call
over Elasticsearch at this size.

## 10 · S3 — The Notifications module does not do notifications

**Files:** `Modules/Notifications/**`

There is no `Notification` entity, and `Shared/Data/BoardSyncDbContext.cs` has no notifications table.
The module is a query over `WorkItemHistory` filtered to the caller's organizations, with a
`Describe` method wording each history row into a sentence.

What follows from that:

- **No targeting.** It returns org-wide activity, not *your* notifications. Nothing checks whether the
  item is assigned to you, mentions you, or is on something you watch. (This is also finding 1.)
- **No read state.** Every call returns the same rows forever. `PATCH /notifications/{id}/read` has
  nowhere to write.
- **No preferences, no watching, no delivery channel.** The `Watcher` and `NotificationPreference`
  entities from the original plan were never built.
- **Only work items generate anything.** Sprint start, sprint close, role grants, and team
  membership changes are invisible, though all of them raise domain events the outbox already routes
  to `Topic.User`.

The `Describe` comment says the type vocabulary is preserved "because clients already switch on those
strings" — worth checking whether any client actually does before the shape is frozen by
compatibility with a frontend that does not exist (finding 7).

**Fix.** A real `Notification` entity written by event handlers off the outbox — the handlers already
run, and `EventTopics` already computes `Topic.User(...)` for exactly the events that should notify
someone. Recipient resolution, `ReadAt`, per-type preferences. Scheduled in
[`../build_context.md` Phase D](../build_context.md#phase-d--notifications-that-notify).

## 11 · S3 — 418 tests, all of them RBAC

`BoardSync.Api.Tests` contains three files: `AccessEvaluatorTests`, `RoleVocabularyTests`,
`EndpointAuthorizationCoverageTests`. They are genuinely good — `AccessEvaluator` is pure, so it is
exhaustively testable without a database, and the reflection-based coverage test is the right kind of
test because it fails for endpoints nobody thought to write a case for.

Everything else has none. No test covers:

- `WorkItemService` — the state machine, hierarchy validation, tag normalization, history
- `SprintService` — 540 lines, the largest service in the codebase
- `Ranking` — fractional midpoints, precision exhaustion, rebalance
- `OutboxDispatcher` — claim, retry, attempt exhaustion, unknown event types
- Any repository, against a real Postgres
- Any endpoint, end to end

Findings 2, 3, and 6 are all things a service-level test would have caught, and 6 would have been
caught by any test asserting sub-second delivery latency.

**Fix.** In priority order: (a) `Testcontainers.PostgreSql` + `WebApplicationFactory` for endpoint
tests — one harness unlocks everything else; (b) `WorkItemService` state machine and `Ranking`, both
pure enough to test directly; (c) an outbox test asserting a domain event reaches its handler in
under a second, which pins finding 6 shut. Do (a) before git sync — webhook ingest is not testable by
hand.

## 13 · S3 — Configuration edges

**Dev JWT secret is committed.** `appsettings.json` carries a pointed comment explaining why
`JwtSettings:Secret` is deliberately absent, and `appsettings.Development.json` then carries a
dev-only value. `ValidateJwtSettings` blocks anything containing `"Development"` from signing a
production token, so the guard works. But the value is public in git forever, which means any
environment that ever falls back to the Development configuration issues forgeable tokens. Move it to
user-secrets (`dotnet user-secrets`) — it costs one command and removes the class of mistake.

**Production password floor is 6 characters.** `SecuritySettings.MinPasswordLength` defaults to 6, and
`ValidateSecuritySettings` requires ≥ 8 in production — so production is safe, but only because the
override is remembered. Raise the default to 12 and let production inherit it. NIST has recommended a
minimum of 8 with no composition rules for years; the config requires uppercase, lowercase, and a
digit at 6 characters, which is the inverse of current guidance — composition rules with a short floor
produce `Passw0rd`.

**`Database:AutoMigrate` in the prod-like stack.** `docker-compose.prod.yaml` sets it true, and
README §4a explains why (no separate migration step). Correct for a local prod-like stack; flag it
here only so nobody copies that compose file to a real deployment.
