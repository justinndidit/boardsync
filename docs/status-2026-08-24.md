# Where BoardSync actually is

**Date:** 2026-08-24
**Scope:** both sides, measured rather than estimated.
**Method:** phase checkboxes from `build_context.md`, the audit register, a
route-by-route diff of the API against every frontend call, and the test suites.

---

## 0. The short version

**The backend is close to feature-complete for v1. The frontend is roughly
two-thirds wired. Neither can ship today, and the reason is neither of them.**

| | Backend | Frontend |
| --- | --- | --- |
| Size | 264 files, 57k LOC | 319 files, 39k LOC |
| Tests | 824, incl. Testcontainers integration | 24, one module |
| API surface | 113 routes | **73 of 113 called (65%)** |
| Broken calls | — | **0** |
| Phases | A–E core shipped; F not started | tracks Phase A–E |

The single most concrete blocker is in neither codebase: **there is no working
path from this repository to a deployed frontend.** §4.

## 1. Backend — what is genuinely left

Phases A–E are shipped in their load-bearing parts. What remains splits cleanly
into *v1 gaps*, *deferred by decision*, and *not started*.

### 1.1 Real gaps in shipped features

| Item | Phase | Why it matters |
| --- | --- | --- |
| **Backfill on link** | C | Walk the last 90 days when a repo is connected, so the first report is meaningful on day one. Needs an outbound provider client — the ingest side is inbound-only today. |
| **ADO merge read-back** | D | Azure DevOps raises `git.pullrequest.merged` for *any* completion, including abandon-with-merge. Without reading the PR back, an abandoned PR can move work to Awaiting QA. Same missing outbound client. |
| **Per-project unbound commits** | C | "Why did my commit not move the card?" is answerable only at org scope today. This is the support-load item. |
| **Notification preferences** | D | Everyone gets everything they are entitled to. The escape hatch is unwatching, which is not the same thing. |
| **Postgres FTS for search** | D | Audit finding 9. Search is a sequential scan with no ranking. |

**None of these blocks a demo.** The first three all wait on the same missing
piece — an authenticated outbound client per provider — so they are one
increment, not three.

### 1.2 Deferred by decision, correctly

GitLab signing tokens, Bitbucket, email delivery, `@mentions`, self-hosted git.
Each has a recorded reason in `build_context.md` §10. Do not let these read as
incompleteness — they are scope, and the scope was drawn deliberately.

### 1.3 The Intelligence half of Phase E

The deterministic metrics shipped as `Modules/Reporting`. **The narrative layer
does not exist**: no `Modules/Intelligence`, no PRD decomposition, no proposal
or acceptance flow, no token budget.

This is the largest single piece of unbuilt backend, and it is the one the
product pitch leans on hardest after git-driven boards. It is also the one with
the least design risk left, because §8.3 already settled the hard part: the
module computes nothing, receives a `SprintReport`, and is instructed to cite
only its figures.

Two smaller items sit with it: the **cumulative flow diagram** (computable from
the same history reconstruction, deferred for size) and **git activity per work
item**, which is *not currently computable* — binding is stateless and no
`CommitLink` table exists. That was the right call for binding; it means commit
counts have nowhere to come from and needs a deliberate decision, not a
discovery mid-report.

### 1.4 Phase F — not started

Instance count > 1 (pgbouncer, `ActivityLogs` partitioning), load testing
against realistic webhook bursts, and a security review focused on webhook
ingest and the integration principal.

**Open decision 8 gates this** and is genuinely unsettled: the deployment target
changes what all three mean. Worth closing before anyone starts.

### 1.5 Audit register

12 of 17 findings fixed, including every S1. Open: 7 (§4 below), 9 (FTS), 13
(config edges), 16 (`ReorderColumnsAsync` emits no event), 17 (orphaned history
index — build the view or drop the index).

Finding 11 — *"418 tests, all of them RBAC"* — is substantially closed: 824
tests now, with a Testcontainers integration harness that has caught real
defects no amount of reading would have.

## 2. Frontend — 73 of 113 routes

**Zero broken calls.** Everything the frontend asks for exists and matches.
What follows is unbuilt, not wrong.

| Module | Called | Total | What is missing |
| --- | --- | --- | --- |
| Rbac | 2 | 2 | — |
| Reporting | 2 | 2 | — |
| Metadata | 1 | 1 | — |
| Notifications | 6 | 7 | `/workspace/notifications` (a legacy alias — nothing missing) |
| Sprints | 19 | 20 | `POST /sprints/{id}/close` |
| OrgProject | 28 | 32 | project roles (3), `GET /orgs/{id}` |
| **WorkItems** | 6 | 15 | **comments, history, links — 9 routes** |
| **Auth/users** | 9 | 19 | **refresh-token, revoke-token, change-password** |
| **Backlog** | 0 | 6 | **the whole module** |
| **GitSync** | 0 | 9 | **the whole module** |

### 2.1 The four real gaps

**Git sync — 9 routes, no UI at all.** The product's central claim cannot be
switched on from the app. Connect an installation, link a repository, read the
delivery log, rotate a secret. Provider verification differs and the UI must
say so: GitHub and GitLab sign payloads; **Azure DevOps cannot**, and
authenticates with a shared secret over Basic auth. Presenting the three as
equivalent would misrepresent the security model.

**Work item detail — 9 routes.** `workItemMapper` hardcodes `comments: []` and
`history: []`. The drawer has tabs for both. Link types carry an inverse
wording — "Blocks" read from the target is "Blocked by" — which metadata
publishes and the client cannot derive.

**Backlog — 6 routes.** A module with its own ordering and sprint-move
endpoints. The backlog UI uses none of them.

**No token refresh.** The session ends when the access token expires. This is
the one item on the list that every user hits, every day.

### 2.2 Quality, honestly

Three alignment increments landed this month: the local permission model
deleted in favour of `/me/capabilities`, the vocabulary moved to
`/api/metadata` (which surfaced `InReview` missing entirely, so git-driven
cards rendered as To Do), notifications rewritten against a shape that had
changed underneath them, and reports wired with the mocks deleted.

Remaining known defects, all recorded:

- `DrawerOverview`'s status and priority pickers **save nothing** —
  `onTaskChange={setEditableTask}`, local state, silently discarded.
- Two drawers and two edit surfaces for the same object.
- 38 eslint errors, ~26 of one class (`set-state-in-effect`) shared by every
  fetch hook in the app. Fixing it means restructuring all of them — a decision,
  not a chore.
- **24 tests, one module.** Capability batching, the identity-keyed cache, the
  state-category grouping, optimistic read markers and `useStateTransitions` all
  shipped on typecheck and reading alone.

## 3. What the two sides do not yet agree on

Nothing, in the sense that matters — no call is broken and no contract has
drifted. Three things are worth naming anyway:

1. **The generated TypeScript client (§5.3) was never built.** Types are
   hand-written on both sides of every boundary. It has held so far because the
   alignment work was done deliberately; it will not hold indefinitely.
2. **`GET /api/metadata` is fetched but only partly consumed.** Roles and
   permissions are published with their inheritance and are still not driving
   the role pickers.
3. **Capability answers are narrower than the rules in one place** — adding an
   item whose parent is already in the sprint is legal for anyone holding
   `sprint:order`, but `sprint:scope` is what gets reported. Documented; the 403
   is the answer there.

## 4. The blocker neither side owns

**There is no working path from this repository to a deployed frontend.**

| Reference | Points at | Reality |
| --- | --- | --- |
| `Makefile: dev-frontend` | `cd boardsync-ui && yarn dev` | wrong path, **and** the project uses npm — no `yarn.lock` exists |
| `docker-compose.prod.yaml` | build context `./boardsync-ui` | **directory does not exist** |
| same, `dockerfile: Dockerfile` | `boardsync-ui/Dockerfile` | **no frontend Dockerfile exists anywhere in the repo** |
| `README` | `boardsync-ui/nginx.conf` | **does not exist** |
| `README` status line | "`boardsync-ui` is still the Vite starter template — the client is not wired to the API yet" | 39k LOC, wired to 73 endpoints |

And underneath all of it: **`ui/` is gitignored at the root.** Even with every
path corrected, a clone of this repository does not contain the frontend, so the
production compose file cannot build it.

This is audit finding 7, which has been open since the register was written. It
has not stayed still — it was "referenced by three build paths and does not
exist"; it is now "exists, is substantial, and every path still points
elsewhere". `make dev-frontend` fails. `docker compose -f
docker-compose.prod.yaml build` fails.

**It is also the cheapest item in this document.** Correct four paths, write a
Dockerfile and an nginx.conf, and decide the repository question — submodule,
monorepo, or two independent deployments. The decision is yours; the rest is an
afternoon.

## 5. So how close is the end?

There is no defined "done" anywhere in this repository, so here is one worth
arguing with.

**A v1 that a team could actually use for a sprint needs, in order:**

1. **Deployment path fixed.** §4. Nothing else can be demonstrated without it.
2. **Token refresh.** Sessions that end mid-sprint make everything else look
   broken.
3. **Git sync UI.** The differentiator, currently unreachable.
4. **Work item comments and history.** Not exotic — every tracker has them, and
   their absence is the first thing anyone notices.
5. **Backlog wired.**

That is the list. Everything else on both sides is either shipped, deliberately
deferred, or Phase F.

**Backend: near feature-complete for that list** — every endpoint those five
items need already exists and is tested. Its remaining work (outbound provider
clients, Intelligence, Phase F) is *beyond* v1, not inside it.

**Frontend: the critical path.** Four of the five items are frontend work, and
the fifth is configuration.

That asymmetry is the real finding. The backend has been the mature side all
month and still is; the question is no longer whether the API can support the
product, but whether the client can catch up to it. It has closed three large
gaps in three increments, so the trajectory is right.

**My recommendation for order:** fix §4 first because it is cheap and blocks
demonstration; then token refresh; then git sync, which is the largest piece
and the one that makes the product itself legible.

Open decision 8 — the deployment target — is worth settling in the same
conversation as §4, because they are the same question asked twice.
